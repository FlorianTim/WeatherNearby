# Prompt — plan template 3.1.0: the To-do reference app

Non-normative (ADR-0005). Copy the fenced block below into a fresh agent
session working in `flutter-app-template`.

It commissions the **planning and specification pass**, not implementation —
AGENTS.md permits code only from an approved story. The pass ends by
producing the first implementation prompt.

═══════════════════════════════════════════════════════════════════════
WHAT 3.1.0 IS
═══════════════════════════════════════════════════════════════════════

The template's example app stops being a three-field smoke test and becomes
a deliberately richer reference application: lists, dates, recurrence,
notifications, Markdown, and JSCalendar interoperability.

The reason is not the to-do app itself. It is that the template needs
something with enough surface to actually break, so that a Flutter release,
a Drift major or a new standard can be tested here before a productive app
is derived from the template.

Two consequences shape every decision in this plan:

  1. THE TEMPLATE STAYS A TEMPLATE. Anything the app needs that is not
     specifically about to-do lists must land in packages/ or core/, never
     buried in features/tasks/. Draft section 14.1 lists these concretely.
     The Markdown editor is the headline case: it goes into
     packages/design_system so that every LumbreCode app has the identical
     text-editing experience.

  2. THE DEMO IS REPLACED, NOT DELETED IN PASSING. Go through the documented
     path: an OpenSpec entry with replace_todo_app: true. Retiring the old
     feature is the LAST slice, not the first — it keeps working until its
     replacement does everything it did.

DELIVERABLES
═══════════════════════════════════════════════════════════════════════

A. Current-state audit
   What the template already provides that the app must reuse rather than
   reinvent: core/permissions (just-in-time flow + rationale sheet),
   core/startup (coordinator), core/settings (SettingDef register),

   Name what is missing and what is thinner than the app needs.
   Verify every claim against the code. The draft may be out of date.

B. OpenSpec entry
   openspec/apps/<slug>.openspec.yaml with replace_todo_app: true, the
   privacy and security blocks, and the reasoning from draft section 3
   recorded so a later reader understands why the demo was replaced.

C. Feature specs under docs/product/specs/
   Use the existing _template/ (8 files each). Propose a split; a defensible
   one is:
     - the task and list domain
     - views, search and navigation
     - notifications and recurrence
     - JSCalendar interoperability (import, export, contract tests)
   Every requirement gets a stable id, every id at least one acceptance
   criterion. Follow the WasThereSomething specs for the level of detail —
   they are the house style.

D. Shared-component plan
   For each item in draft section 14.1: target location, public API sketch,
   and which slice extracts it. Be explicit that extraction happens in the
   slice that introduces the component, not "later".

E. Data contract and Drift migration design
   The draft's section 7 schema, checked against the template's current
   database. Foreign keys enforced, transactions for multi-table writes,
   additive migrations with a fixture test per version, an explicit
   sort_order column (never order by a timestamp).

F. ADRs where warranted
   Likely candidates: the notification boundary, the Android receive
   boundary, and the reference-app decision itself. WasThereSomething's
   ADR-0016, ADR-0019 and ADR-0020 are the precedents for tone and depth.

G. Implementation plan
   docs/delivery/implementation-plans/, the slices from draft section 16,
   each shippable and reviewable. Slice 0 is the shared foundations, slice 1
   is packages/task_interchange with no UI, slice 13 retires the demo.

H. Test strategy
   Domain, serialization, database with migration fixtures, widget, and the
   contract tests CT-1..CT-15 from the interoperability guide section 12 —
   loading the SAME golden fixtures WasThereSomething tests against.

I. AGENTS.md amendment
   The preservation rule must now protect the new reference app AND say what
   it is for, so the next maintainer does not simplify it back into a demo.

J. A first implementation prompt for slice 0.

## If you want implementation instead of planning

Append to the block above:

```text
After presenting the plan, do not stop: implement slice 0 (shared
foundations) as a single reviewable change. Create the story first, then the
code. Run `./scripts/validate.sh` (or flutter analyze + flutter test) and
report the result honestly, including anything you could not run.
```

## Why the planning pass comes first

AGENTS.md is explicit: agents may implement code only from an approved story
or an explicit task issue. A prompt that jumps straight to code would ask
the next agent to break the repository's own rule on its first action —
which is a poor way to start a change that is meant to become the reference
for every future app.
